# VRover 架构构想（Design Vision）

> **状态：构想阶段，尚未实现。** 本文记录方向性设计，供研究对照与后续规划。
> 当前已落地的是首版骨架（`Platform` / SoM / agent loop / MockPlatform），见 [index.md](./index.md)。

## 一句话

把 Visual Tool 做成一个**独立运行的本地 server**：它接入某个图形窗口 / 远程桌面 / 手机，把应用建模成一张 **UI 图**（每屏一个 node，视图切换控件是 edge），以 **graph walker** 的形式为 AI 提供从底层（click / type）到高层（`go_back`、`open_article(id)`）的操作；用纯文本 **DSL** 持久化整张图，AI 能基于 DSL 为新应用生成 / 扩展图并反哺工具；同时对外提供**人类 JS 脚本 API**。

## 核心构想

1. **胖工具 / 本地 server**：Visual Tool 独立进程运行，负责真实接入图形目标。语言无关、可远程、可独立重启、可同时服务多个客户端。
2. **UI 图 + graph walker**：`node` = 一个界面 + 其可交互控件；`edge` = 由「视图切换控件」维护的界面跳转。walker 在图上导航、执行操作。
3. **分层操作 + 动态注入**：底层 `click / type / scroll / keypress` 之上，提供 `go_back`、`open_article(article_id)` 等高层操作；这些操作**按「当前 node」动态注入** AI 当轮上下文。走高层操作时，AI 甚至不必关心具体 UI。
4. **DSL 持久化 + AI 反哺**：纯文本 DSL 存整张图；AI 面对新应用时，可基于 DSL 语法**生成 UI 图**，反哺工具，形成闭环（探索 → 建图 → 持久化 → 复用）。
5. **人类脚本 API**：同一套图 + 操作对外暴露 JS 接口，程序员可编写自动化脚本；脚本能沉淀 / 修正图，供 AI 复用。

## 三层架构

```
┌──────────────────────────────────────────────────┐
│  AI brain（TS，现有 loop + 可注入 complete）         │
│   每轮只拿到：当前 node + 该 node 的动态高层操作     │
└────────────────┬─────────────────────────────────┘
                 │ go_back / open_article(id) / 走不通时回退 SoM
┌────────────────▼─────────────────────────────────┐
│  Visual Tool（胖工具 · 本地 server）                │
│   · UI 图：node(一屏+控件) ──edge(视图切换)──▶ node   │
│   · graph walker：导航 / 执行高层操作 / 维护遍历栈    │
│   · DSL 纯文本持久化 + 人类 JS 脚本 API             │
│   · 图里没有 / 控件漂移时：回退 SoM 感知去建图·修图    │
└────────────────┬─────────────────────────────────┘
                 │ 底层 click/type/scroll/keypress + capture/getElements
┌────────────────▼─────────────────────────────────┐
│  Platform 驱动（本地窗口 / 远程桌面 / 手机 / 浏览器）  │
└──────────────────────────────────────────────────┘
```

## 与现有代码的关系（演化，非重写）

- `Platform`（capture / click / type…）→ **最底层驱动**，graph walker 用它去实际操作应用。
- `src/som/` SoM 标注 → **感知引擎**：建图时识别控件、走图失败时重新定位；承载「无障碍树 + ML 视觉结合」（见 [visual_tool.md](./visual_tool.md)）。
- agent loop 的「可注入 `complete` + 可注入工具定义」→ 用来**按 node 动态注入高层操作**。
- `done` / `TaskResult` 等契约不变。

## 执行模型：图优先，视觉兜底

- **已知边走图**：确定性、快、不必每轮看屏。`go_back` 几乎白捡——walker 维护遍历栈，`go_back` = pop。
- **未知 / 漂移回退 SoM**：图里没有当前 node，或记录的控件已消失时，回退视觉感知重新定位 / 建边。
- 这把「纯图」与「纯视觉」的两难解掉：图负责高频已知路径，视觉负责探索与自愈。

## 关键概念

| 概念 | 说明 |
|---|---|
| **node** | 一个界面 + 控件集 + 一个稳定签名（用于判同） |
| **edge** | 从 node A 经某控件跳到 node B（记录触发控件 + 效果） |
| **高层操作** | 按 node 暴露的语义动作：结构相对型（「点列表第 1 项」）或语义标签型（`open_article(id)`） |
| **遍历栈** | 支撑 `go_back` / 历史回溯 |

## 硬骨头（按难度）

1. **节点身份（同一界面的判定）**：滚动 / 动态内容 / 加载态会让"同一屏"长得不一样，不同屏又可能结构相似。这是图稳不稳的地基。**取向**：控件集结构签名（角色 + 相对布局 + 稳定标签，归一化）打底；native id（activity / URL / DOM route）有就用，作为强锚点。
2. **模板化 / 参数化节点**：`open_article(id)` 意味着"文章列表"是结构固定、内容可变的节点，要把 id 映射到具体项。DSL 必须支持参数化节点，否则只能退到「点第 N 项」这种相对操作。
3. **DSL 合并与自愈**：AI 反哺生成的图怎么校验、合并而不破坏已有；应用升级导致控件漂移时怎么容忍（丢了就走视觉兜底重建边）。
4. **探索预算**："穷举常用 UI"是理想，现实是有界贪心探索 + 任务驱动增量。

## 增量路线（最小验证先行）

| 里程碑 | 内容 | 验证什么 |
|---|---|---|
| **M1（建议先做）** | UI 图数据模型 + DSL 草案 + **in-process** graph walker；把现有 Mock 扩成多屏小应用（登录→主页→文章列表→文章） | 建图、`go_back` 沿边回退、按 node 动态注入高层工具。不引 server、不接真平台，全复用现有 Platform / loop |
| **M2** | 节点身份签名 +「图优先 / 视觉兜底」降级路径 | 走图失败时自动回退 SoM 重新定位 |
| **M3** | server 化（定义协议，独立进程 / 可远程），brain 经 `RemotePlatform` 接它 | 工具与大脑解耦、可远程驱动 |
| **M4** | AI 闭环（基于 DSL 生成 / 扩展图，校验合并）+ 人类 JS 脚本 API | 新应用自动建模、脚本沉淀图 |
| **M5** | 真平台接入（桌面 / 手机 / 浏览器） | 落地真实自动化 |

## 待定的设计决策

1. **第一刀切哪？** 倾向 M1（图模型 + walker + 多屏 mock）。备选：server 优先 / 独立 explorer 优先 / DSL 优先。
2. **高层操作的语义起点**：先做**纯结构相对**（"点列表第 1 项"、"返回上一屏"）够不够起步？还是一开始就要 AI 给控件打语义标签（article / submit）支撑 `open_article(id)`？倾向先纯结构相对，语义标签作为 DSL 里一层**可选标注**后加。
3. **walker 进程位置**：先 in-process 跑通概念，再 server 化？倾向是。

## 参考脉络（便于对照研究）

> 这些都是把「应用建模成可导航图」思路的不同侧面，研究时可对照其节点身份、建图策略、操作抽象。

- **Model-based GUI 测试**：把应用建模成 FSM / 状态图，按模型生成测试路径。代表：**Stoat**（移动端 GUI 转移模型 + 模糊）、**GraphWalker**（模型库 + 路径生成）、Appium + 模型。
- **AutoDroid**：LLM + app「常识知识图」+ function tree，用图 / 类 DSL 表达「怎么做任务」。
- **AppAgent**：探索阶段为每个元素建「操作文档」知识库，先学后用（边学边记效果）。
- **App Crawler / Android Monkey**：自动化遍历建图（无语义，覆盖导向）。
- **Mobile-Env / AndroidWorld**：交互环境 + 任务评测，可看其如何定义状态与转移。
- 高层操作 ≈ 强化学习里的 **options / skill library**；DSL ≈ 面向自动化的程序合成。

VRover 想做的差异化：**感知（SoM）+ 图（UI graph）+ 分层操作（按 node 动态注入）+ DSL（AI 反哺闭环）+ 人类脚本** 一体化。
